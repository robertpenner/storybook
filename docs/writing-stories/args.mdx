A story is a component with a set of arguments that define how the component should render. “Args” are Storybook’s mechanism for defining those arguments in a single JavaScript object. Args can be used to dynamically change props, slots, styles, inputs, etc. It allows Storybook and its addons to live edit components. You _do not_ need to modify your underlying component code to use args.

When an arg’s value changes, the component re-renders, allowing you to interact with components in Storybook’s UI via addons that affect args.

Learn how and why to write stories in [the introduction](./index.mdx). For details on how args work, read on.

## Args object

The `args` object can be defined at the [story](#story-args), [component](#component-args) and [global level](#global-args). It is a JSON serializable object composed of string keys with matching valid value types that can be passed into a component for your framework.

## Setting args through the URL

You can also override the set of initial args for the active story by adding an `args` query parameter to the URL. Typically, you would use [Controls](../essentials/controls.mdx) to handle this. For example, here's how you could set a `size` and `style` arg in the Storybook's URL:

```
?path=/story/avatar--default&args=style:rounded;size:100
```

As a safeguard against [XSS](https://owasp.org/www-community/attacks/xss/) attacks, the arg's keys and values provided in the URL are limited to alphanumeric characters, spaces, underscores, and dashes. Any other types will be ignored and removed from the URL, but you can still use them with the Controls panel and [within your story](#mapping-to-complex-arg-values).

The `args` param is always a set of `key: value` pairs delimited with a semicolon `;`. Values will be coerced (cast) to their respective `argTypes` (which may have been automatically inferred). Objects and arrays are supported. Special values `null` and `undefined` can be set by prefixing with a bang `!`. For example, `args=obj.key:val;arr[0]:one;arr[1]:two;nil:!null` will be interpreted as:

<CodeSnippets path="storybook-args-url-params-converted.md" />

Similarly, special formats are available for dates and colors. Date objects will be encoded as `!date(value)` with value represented as an ISO date string. Colors are encoded as `!hex(value)`, `!rgba(value)` or `!hsla(value)`. Note that rgb(a) and hsl(a) should not contain spaces or percentage signs in the URL.

Args specified through the URL will extend and override any default values of args set on the story.

<Callout variant="warning">

If you're using Storybook's hooks API in the story's render function, **do not** mix them with React's hooks such as `useState`, `useEffect`, or `useRef`. This is because side effects and re-rendering triggered by React's hooks do not run through Storybook's hook context, which can cause an error on re-render. To manage state and side effects within a story, you must use Storybook's equivalent hooks, such as `useState`, `useEffect`, and `useRef` from `storybook/preview-api`.

### Continuous args interactions

Use `useArgsInteraction` from `storybook/preview-api` to opt into continuous updates during a slider gesture. Ordinary `useArgs` updates keep their existing lifecycle.

```tsx
import { useArgs, useArgsInteraction, useRef } from "storybook/preview-api";

function Render() {
  const [args] = useArgs<{ value: number }>();
  const interaction = useArgsInteraction<{ value: number }>();
  const active = useRef(false);
  const latestInput = useRef(args.value);
  const begin = () => {
    if (!active.current) {
      latestInput.current = args.value;
      active.current = interaction.begin();
    }
  };
  const finish = () => {
    if (!active.current) return;
    active.current = false;
    void interaction.finish({ value: latestInput.current }).then((result) => {
      if (result.status === "failed") {
        console.error("The final args interaction failed", result);
      }
    });
  };

  return (
    <input
      type="range"
      value={args.value}
      onPointerDown={begin}
      onChange={(event) => {
        latestInput.current = Number(event.currentTarget.value);
        interaction.update({ value: latestInput.current });
      }}
      onPointerUp={finish}
      onPointerCancel={() => {
        active.current = false;
        void interaction.cancel();
      }}
      onKeyDown={(event) => {
        if (
          [
            "ArrowLeft",
            "ArrowRight",
            "ArrowUp",
            "ArrowDown",
            "Home",
            "End",
            "PageUp",
            "PageDown",
          ].includes(event.key)
        ) {
          begin();
        }
      }}
      onKeyUp={finish}
      onBlur={finish}
    />
  );
}
```

`begin()` checks the preview's advertised capability before starting an interaction. A busy canvas may still reject the request as `unsupported`; updates then use the ordinary path. If the rejection arrives after inputs or release, the client replays their merged latest args through ordinary updates, including newer edits delivered while finishing. Cancellation suppresses this replay. The result remains `unsupported` and does not certify that ordinary render's completion. During a supported interaction, Storybook serializes canvas updates and replaces obsolete pending values. Intermediate updates use the last completed loaded data and defer loaders, hooks, animation settling, reports, and automatic accessibility audits.

The example records the value delivered by `onChange`. React can restore a controlled range's earlier value before `keyup` while the canvas update is pending, so a finish handler should use the recorded input value.

`finish()` commits the exact final args and returns a typed result. A `completed` result means that the final canvas, required loaders and hooks, animation settling, accessibility audit, reports, and args acknowledgement have finished. If final loaders change the loaded data, or before hooks require rendering again, Storybook performs that render. It reuses an already rendered final canvas only when the final render inputs still agree.

`cancel()` restores the args from the start of the interaction when the same story is still active. Its `cancelled` result means the session stopped; the ordinary restoration render may still be running. Navigation or teardown cancels pending work without changing the new story. A failed transient renderer logs its error and attempts an ordinary final render; a failed or cancelled final render does not return `completed`.

A reset, ordinary args update, globals update, remount, or hot update stops an active interaction. Storybook runs the ordinary lifecycle for the resulting args, and an old finish request cannot overwrite them. A hot update preserves the client so it can begin another interaction for the same story. Calling `update()` without an active interaction also uses the ordinary path. Begin a new interaction to certify a subsequent value.

Explicit test environments, play functions, destructured `mount`, docs renders, renders using initial args, and previews without this capability use ordinary args updates. Their interaction result is `unsupported`, so callers must not interpret it as verified final completion. Manual accessibility requests retain their existing behavior.

</If>

## Mapping to complex arg values

Complex values such as JSX elements cannot be serialized to the manager (e.g., the Controls panel) or synced with the URL. Arg values can be "mapped" from a simple string to a complex type using the `mapping` property in `argTypes` to work around this limitation. It works in any arg but makes the most sense when used with the `select` control type.

<CodeSnippets path="arg-types-mapping.md" />

Note that `mapping` does not have to be exhaustive. If the arg value is not a property of `mapping`, the value will be used directly. Keys in `mapping` always correspond to arg _values_, not their index in the `options` array.
